1. Project Overview

1.1 What the Bot Does

This is an automation bot for the Pokemon TCG Pocket (PTCGP) mobile game, running many instances of the game inside the MuMu emulator. It reads the screen via template image matching ("needle" search) and drives the game through ADB shell input. Main capabilities:

  • Pack-opening rerolls: creates new accounts (Create Bots 13P) or injects saved account XMLs (Inject modes), opens packs, and detects god packs, tradeable cards, and wishlisted cards.
  • God pack verification (GP Test): the Main.ahk instance verifies god-pack accounts from the friend list via the Wonderpick screen.
  • Friend management: add by friend code, remove all, approve requests, showcase likes (Stage\FriendManager.ahk).
  • Missions and rewards: daily missions, beginner-mission grinding, gift packs, Wonderpick, event rewards (Stage\MissionAndRewards.ahk).
  • Account management: account XML extract/inject, per-account JSON metadata (pack counts, flags, shinedust), scheduling/eligibility, snapshot & corruption repair.
  • Hourglass spending (HourglassSpend), wishlist matching (Wishlist), Discord webhook notifications, a web card dashboard, and a third-party plugin system (17 hook targets).

1.3 Recurring Design Patterns

  • Facade-preserving refactoring: bundles of free functions get moved into classes (static namespaces) while thin delegating wrappers with identical names/signatures stay behind for the hundreds-to-1,600 existing call sites. Examples: ADB.ahk→Emulator, part of Utils.ahk→Host, Logging/Profiler/DiscordLogger→Diagnostics, Recognition\CardDetection.ahk→PackAnalysis.
  • Mechanism/policy separation: ScreenSearch (pure search mechanics) contains no failure-recovery policy; FindImageWithAction (the policy layer) owns stuck-recovery (restartGameInstance).
  • Load-time dependency stubs: AHK v2 silently halts at load time when a function body references an undefined name. Cockpit/LaunchAllMumu therefore declare minimal stub classes for Host/Emulator instead of including the heavy real ones, just to pass the static load check. (Monitor.ahk used to stub too, but it actually calls Emulator.GetInstallFolder() at runtime — the empty stub caused a measured false "no MuMu folder" exit on 2026-08-07, so it now includes the real classes and stubs only CreateStatusMessage.)
  • Atomic file writes: write to a tmp file, then swap with FileMove(…, 1) — used consistently across Metadata/History/AccountStore/CockpitState. Deliberately not used for Scripts\N.ini, a multi-producer file where a whole-file rewrite would revert keys written by other paths in between (documented in CockpitInstancePush.ahk's header).
  • Self-declared dependencies: library files #Include their own dependencies anchored on %A_LineFile%, so paths never break regardless of which entry point pulls them in.

5.2 The Account Domain Axis

AccountStore (1,407 lines, 72.2KB) — extends Metadata

  • Storage shape: one account = one document at Accounts\Cards\accounts\<deviceAccount>.json (instance methods ReadUnlocked/WriteUnlocked). A legacy multi-account store Accounts\Cards\metadata.json is kept for never-migrated accounts.
  • Concurrency: named mutex Global\PTCGPB_AccountStore (static LockName). Document saves use Metadata's tmp-then-rename.
  • Business logic (all static): NewAccount/AccountFromObject/AccountToObject (JSON object ↔ account Map conversion), FindKey/EnsureAccount/MergeAccount, LoadAccount/SaveAccount/SaveTempAccount, flags via NewFlag/SetFlag/ClearFlagEverywhere, SetShinedust/SetLastPackPulledNow/SetLastLoggedInNow/SetLanguage, filename parsing ExtractPackCount/ExtractCreatedAt, queue-entry removal RemoveByNameOrIndex/RemoveByIndex.
  • Snapshot/repair (flow in §10.3): SnapshotAccounts() (line 200), RepairAccountsFromSnapshot() (line 316), RepairAccountFileIfCorrupted() (line 400). MCode acceleration + streaming archive writes (a 172MB in-memory string concatenation that took 2m05s was replaced by streaming — measured, per in-source comments).
  • Dashboard support: GatherDashboardPaths (line 500), BuildDashboardPayload (line 588), BuildDashboardManifestSignature — account data collection used by the HTTP routes.

Mission (mission flags B/X/T/R)

Unifies what used to be two representations of the same data (the session's missionDoneList and the account record's flags["B"/"X"/"T"/"R"]). Load(accountMeta) converts flags→fields, and if the T flag's 5-day validity has expired it resets the field to 0 and returns true so the caller must write it back with Flush() (I/O deliberately moved out of the method). Flush(accountMeta) does the reverse conversion and recomputes T's validUntil. Flag semantics: B=beginner missions done, X=special missions done, T=pack in testing (5 days), R=gift received.

History (pull records + record-only flags H/W/SH)

RecordPull(pack, cards) — writes directly and atomically into the account JSON's pulls array, independent of the AccountStore mutex (a faithful move of the historically separate LogSinglePullToCardDatabase write path). SetHomeReached() (H), SetWonderPick(validUntil) (W, 24h), SetSpendHourglass() (SH, 24h) — these flags are write-only (never read back anywhere in the repo; verified by grep per the header comment).

AccountEligibility (eligibility rules)

A collection of mostly-pure static predicates: HoursSince/ToUTC/CurrentDailyResetUTC (06:00 UTC reset), WasAfterDailyReset/GetFlag/FlagIsExpired, etc. Only InjectRewardsEligible/InjectPackEligible/IsEligible are impure (they read botConfig).

AccountScheduler (750 lines, 38.3KB) — port of the carddb.exe Rust logic

A 1:1 port of the old Rust subcommands, with the original function and line number noted above each method: ScheduleAccounts (main.rs:2752), CountEligibleForAllInstances (main.rs:2844), BalanceXmls (main.rs:3147). It keeps its own Eligible/PackCountAllowed (1:1 with Rust's eligible()) instead of using AccountEligibility.IsEligible, because the latter mixes in the wonderpick min-packs check and would diverge from Rust for accounts without metadata.

AccountQueue

ScanNext(scriptName, saveDir) — scans Accounts\Saved\<N>\list_current.txt for the next injectable account, returning a 1-based index into the file after ineligible entries were removed and rewritten. The header documents in detail why this file cannot be merged into AccountStore: it is a load-time dependency boundary (four entry points include AccountStore without the names ScanNext's body references).

5.3 The Machine-Control Axis: Emulator and Host

Emulator (926 lines, 48.4KB)

Everything about one MuMu instance and its ADB channel. There are two command channels, and they are never mixed (header comment):

  1. ADB channel → RunAdbCommand(): talks inside the Android guest. Requires a booted guest and a live ADB connection.
  2. MuMuManager channel → RunManagerCommand(): a host executable controls the instance itself (launch/shutdown/restart/setting/info). Works even when the guest is off — it is how instances get turned on in the first place.

Selected methods (of ~47): install-folder discovery GetInstallFolderFromConfig/GetInstallFolder (config json → Settings.ini folderPath fallback, iterating 7 subfolder names), IsV5/GetVersionBias, connection lifecycle ResolveBaseInfo/FindPort/ConnectDevice/InitializeShell/EnsureShell/ReconnectAfterInstanceRestart, PTCGP app control StartPtcgpApp/ClosePtcgpApp/TerminatePtcgpProcess/WaitForPtcgpAppFocus/IsHomeScreen/HasPtcgpAppCrash/DumpLogcatToFile, input Tap/TapWithBBox/InputText/SendKeyEvent/Swipe/SendGesture, CaptureScreenshot.

Host (396 lines, 19.0KB, static namespace)

Everything the bot demands of the host Windows machine: PDH GPU performance counters (the handle must have exactly one owner per process, hence no instantiation), GetInstanceGpuMemory (WMI PID lookup cached in gpuPidCache, validated only with ProcessExist), cover-window management (FindCoverWindow/IsIgnoredCoverWindow/Restore…), instance processes LaunchInstance/TerminateInstance/GetInstancePid/RestartInstance, ReloadScript. The 20 functions moved here remain in module\Utils.ahk as same-name delegating wrappers.

6.2 Recognition\ — Needle Search, OCR, Error Popups

ScreenSearch.ahk — Needle Search as a Service (no policy)

A service class absorbing the "capture window → look up needle → search → (repeat an action)" logic that was independently implemented three times in Main.ahk, 1.ahk and _SendFriendRequest.ahk.

  • Search(hwnd, needleName, opts): one-shot capture+search. Returns the match position ("x,y") or false. Calls ErrorCheckInScreen on the captured frame via dynamic lookup (callers that don't include the error module silently skip it — only the lookup is wrapped in try; the actual Call is not swallowed).
  • SearchIn(bmpPointer, imageName, x1,y1,x2,y2, variation): re-searches an already-captured frame (so N needles against the same frame cost only one capture).
  • SearchWithAction(hwnd, needleName, actionFn, opts): repeats actionFn until found. Separate pollIntervalMs (default 100) and actionIntervalMs (reproduces the original "search every 100ms, click every sleepTime ms" split), giveUpTimer (expiry→return false), stuckTimer+onStuck (expiry→corrective callback, then Reset — the loop keeps going).
  • NeedlesDir(): getScriptBaseFolder()\Scripts\Needles\ — independent of the caller's A_ScriptDir.
  • Why it lives in module/: it depends on needlesRegistry (game data). It composes GDIPService (does not extend it) — GDIPService is a peer edge-facing API, not a base class (header comment).
  • Why no recovery policy here: Search/SearchWithAction are pure mechanics. Building a Timer and deciding what Expired() means (give up vs. restart) is each caller's job — that policy layer is FindImageWithAction.

FindImageWithAction.ahk — the Unified Find+Act Primitive (policy layer)

Replaces the old FindOrLoseImage/FindImageAndClick (duplicated with subtly different definitions in 1.ahk and Main.ahk). Owns the stuck-recovery policy (restartGameInstance).

9.2 The Card Art Pipeline — Cloudinary Migration (2026-08-10)

Card art used to be served from crinitys.github.io; ~14,000 images pushed that repo past the GitHub Pages 1GB publishing limit, so the originals were re-uploaded to Cloudinary. Both consumers now build the same URL shape, https://res.cloudinary.com/crinitycloud/image/upload/images/<lang>_<country>/<illustrationId>.png (no version segment needed — verified against the live host):

  • The bot: PackAnalysis.Render.GetCardArtImage(illustrationId, lang, country, cacheDir) (PackAnalysis.ahk:1223) — downloads one card's art for the synthetic pack image posted to Discord, validating the response by PNG signature (a 200-with-HTML shim page would otherwise get cached as a "valid" image forever).
  • The dashboard: Route_CardImagesPrefetch.ahk ("Use local card images") — bulk-prefetches every unique illustrationId from Helper\cardmap.json using ~20 concurrent async WinHttpRequests pumped from a timer (AHK is single-threaded; sequential download of thousands of cards would take tens of minutes). Returns 202 + a polled /card-images/status; a server stop also stops the downloads (DashboardServer.OnStop).

9.3 The Per-Locale Image Cache

The download cache is Cache\CardImageCache\<lang>_<country>\<illustrationId>.png — split into per-locale subfolders as of 2026-08-10, because some cards keep the same illustrationId across languages with different artwork; a single flat folder returned the previous language's cached art after a language switch (measured user report). Consumers:

  • The bot picks the locale from the loaded account's language metadata (via GetCardArtImage's lang/country parameters).
  • The dashboard has no account context, so the host GUI (DashboardServerHost.ahk) offers an 11-locale picker (en_US … id_ID) that sets DashboardServer.CardImageLocale; prefetch and serving both key off it.
  • Serving to the browser goes through GET /card-image/<illustrationId> (Route_CardImage.ahk, a RoutePrefix route) — the old page GET the cache folder directly, which only worked because the whole install folder was the web root. The route sanitizes the id, refuses paths that resolve outside the cache dir, and serves with public, max-age=86400 (card art never changes).

10.4 ADB Command Execution — Persistent Shell vs. Separate Processes

[Establishing the resident shell: Emulator.InitializeShell()]
  WScript.Shell.Exec("adb -s 127.0.0.1:<port> shell")   ← one resident process
  → StdIn.WriteLine("su")                                  ← root elevation
  → on failure: disconnect/connect (CmdRet = separate processes), then backoff retry (max 5)

[Normal commands: Emulator.RunAdbCommand(command, isReturnning, timeoutMs)]
  StdIn.WriteLine(command . ";echo;echo done;")
    ─ the bare `echo` is the key: for commands whose output does not end in a
      newline (e.g. cat), the marker would glue on as "…}done" and ReadLine
      would block forever; the empty echo guarantees the marker starts its own line
  Loop StdOut.ReadLine():
    line = "done"  → complete (returns the accumulated output if isReturnning)
    timeout check  → only fires between lines. If the shell goes fully silent,
                     ReadLine blocks inside the COM call — that case still hangs,
                     and the only signal is a "send" trace without a matching
                     "done" (in-source comment)
    dead shell     → InitializeShell() reconnects, then retry
  On failure: up to 3 retries; only when exhausted is adbShell reset + EnsureShell()
    (previously the catch unconditionally reset the shell, so the next iteration
     always died with "String has no StdIn" — per the measured comment, 2 of 3
     retry failures were manufactured by that self-reset)

[Commands that run as separate processes, and why]
  · adb connect / disconnect (CmdRet)
      → they create/tear down the connection itself, so they cannot ride the
        resident shell that lives on that connection
  · the 4 pm disable-user commands in DisableBackgroundServices
      → each runs "adb -s ... shell pm ..." independently — executed before
        the resident shell is initialized
  · Emulator.TerminateAdbProcesses
      → kills the host's adb.exe itself via ProcessClose+taskkill (host process
        control, not a channel command)
  · the MuMuManager channel (RunManagerCommand: launch/shutdown/restart/setting)
      → instance-level control that must work with the guest powered off — its
        failure modes differ from ADB's, which is why no generic RunCommand
        wrapper exists (Emulator.ahk header)

[The two screen-capture paths]
  · GDIPService.CaptureWindow          : host-side PrintWindow (default, fast)
  · GDIPService.CaptureViaAdbScreencap : guest-side screencap -p | base64
      → streamed over the resident shell between ---START---/---END--- markers

Include conventions: (1) libraries #Include their own dependencies anchored on %A_LineFile%. (2) Domain classes (module\classes\*) carry no includes of their own — the entry points own the include lists, which is what makes Cockpit's stub substitution possible, and what made the seven-folder reorganization a pure path rename. (3) A few cross-module calls (ErrorCheckInScreen, bboxAndPause_immage) are resolved via %"name"% dynamic lookup, turning them into optional dependencies. (4) The plugin manifest is included with #Include *i (optional) and after the botConfig assignment — plugin registration logs through Diagnostics, which reads botConfig at call time.

12.1 SelfChecks (25 files)

Headless self-verification scripts. They are the safety net built after repeatedly hitting AHK v2's "load silently halts on an undefined name reference" trap in production. Highlights:

  • EntryPointLoad_selfcheck: launches all 12 entry points as real AHK processes and verifies clean loads. Its method is documented at length in its header: a same-folder wrapper (#Warn VarUnset, StdOut + ExitApp + #Include <entry point>) makes the AHK v2 loader itself do full name resolution with zero code executed — the exact warn mode was chosen by measurement (All,Off passes silently; default pops a modal; All,StdOut drowns in irrelevant LocalSameAsGlobal warnings). 13. The Plugin System (module\Plugin\)

The third-party extension point, introduced 2026-08-09 and now housed in its own Scripts\module\Plugin\ folder. Each folder under the repo-root Plugins\ directory is one plugin; on every StartBot, PluginEngine_GenerateManifest() in PTCGPB.ahk (line 2951, invoked at line 2658 — once, before the worker copies, since every instance shares the single generated file) scans and validates them, then generates instantiation code into Scripts\_plugins.g.ahk. Workers pull it in with #Include *i so a missing manifest never breaks a standalone load. For the full usage guide and API reference see docs\Plugin\README.md (Korean) / README-en.md (English) — this section only summarizes the architecture.

13.1 Role Split — Plugin vs. PluginEngine

  • Plugin\Plugin.ahk (154 lines): the parent class plugin authors inherit from. It owns the hook-target catalog (HOOK_TARGETS, 17 entries), the ctx-field catalog each target.when can carry (CTX_SHAPES, 35 entries), the state-access gate (SessionRead/SessionWrite/ConfigRead/SaveValue/LoadValue/GetPlugin), and developer convenience functions (Log/TimerStart/TimerEnd/Dump/Screenshot — all swallow their own failures, so a debugging helper can never three-strike the hook it was inspecting).
  • Plugin\PluginEngine.ahk (271 lines, 18.9KB): owns instance registration (RegisterInstance), conflict resolution (ResolveConflicts), dispatch (Fire), and the timeout watchdog (CheckHookTimeout). It only references Plugin.ahk's catalogs and keeps no copy of its own — "Plugin defines, PluginEngine validates and fires."
  • The 17 hook targets: RunPhase/Wonderpick/FriendAdd/FriendRemove/InstanceRestart/DailyMission/SpecialMission/Gift/Hourglass/Showcase/PackOpening/GodPack/AccountExhausted/StuckRestart/BeginnerMission/Tutorial/FoundTradeableCard — each overrides whichever of beforeEvent(ctx)/afterEvent(ctx)/onItem(ctx) its target supports (onItem exists on the four per-item targets: FriendAdd/FriendRemove/SpecialMission/Showcase).

13.2 ctx Drift Detection — Catching Doc/Code Mismatches Automatically

Right before Fire() invokes a hook, it diffs the actual ctx's fields against Plugin.CTX_SHAPES's declaration and logs a warning to Logs\Plugins.txt for any undeclared field (_CheckCtxDrift) — a signal that "the code has moved ahead of the catalog." Every ctx gets a Get(key, default) auto-attached via DefineProp so conditional fields (e.g. GodPack.after's cards, an empty string on the fallback path) can be read safely — the same convention as session.get()/botConfig.get(). Rich payloads include PackOpening.after (cards/shinedust/pack/lang/country/raw/stopEarly) and StuckRestart.before (reason/callerFile/callerLine/RL).

13.3 The Four Safety Mechanisms

  • Three-strikes, with a one-strike exception: 3 consecutive exceptions from the same target.when disables it for the rest of the session. But PropertyError/MethodError (accessing a nonexistent property or method) are deterministic — a retry would fail identically every time — so those disable it immediately, on the first occurrence, with no three-strikes grace.
  • Conflict resolution: if 2+ plugins implement the same hookTarget+method, the one whose class name sorts first alphabetically wins; the losers are silently skipped for that method only, not disabled entirely. This is decided once per StartBot — if the winner is later three-striked out, the runner-up does not take over.
  • Reentrancy guard: when CheckHookTimeout() detects a hung hook and calls restartGameInstance(), that call can itself fire the StuckRestart hook, re-entering Fire(). currentHook is saved on entry and restored afterward, so the watchdog's tracking of the outer (hung) hook survives the reentrant call.
  • Timeout watchdog: any hook that exceeds HOOK_TIMEOUT_MS (5 minutes) is force-restarted via the existing stuck-recovery path (restartGameInstance). Because this runs off a SetTimer callback, it cannot interrupt a pure tight loop with no Sleep in it — best-effort protection, not a hard kill.

13.4 The Plugin Manager UI

PTCGPB.ahk — main window → Tools & System Settings → Plugin Manager. A GUI for enabling, deleting, and inspecting conflicts without hand-editing plugin.ini. The status column color-codes each plugin as ✅ (healthy) / ⚠️ (structurally valid but some methods disabled by conflict) / ❌ (failed structural validation) / 🔴 ("dead plugin" — no callable methods at all), with the reason shown as a hover tooltip on ⚠️/🔴 rows.
