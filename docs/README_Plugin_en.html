PTCGPB Plugin Guide

English edition of docs\Plugin\README.md - content is equivalent.

This document and the example code live in docs\Plugin\, not in the repo root's Plugins\ (moved 2026-08-09) - because even example plugins risk being accidentally activated if they sit in the Plugins\ folder that actually gets scanned. To try an example, copy the whole folder you want from docs\Plugin\examples\ and paste it into the repo root's Plugins\ folder - Plugins\<copied folder name>\plugin.ini and main.ahk must survive the copy intact.

Each subfolder under the repo root's Plugins\ folder is one plugin. Every time the bot starts (StartBot), PluginEngine_GenerateManifest() in PTCGPB.ahk scans that folder and, for every plugin that passes validation, generates instantiation code into Scripts\_plugins.g.ahk as well, which the workers (1.ahk and its clones 2.ahk, 3.ahk, ...) then load.

Minimal Setup

Plugins\
  MyPlugin\
    plugin.ini
    main.ahk

plugin.ini:

[Plugin]
Name=MyPlugin
Class=MyPlugin
Main=main.ahk
Enabled=1
  • Name: must exactly match the folder name. If it doesn't, the loader simply skips it (it won't be included in Scripts\_plugins.g.ahk, and the reason is logged to Logs\Plugins.txt).
  • Class: a new key - specifies which class in main.ahk to use. The class name doesn't have to match Name (the folder name); you're free to name it however you like.
  • Main: the entry file. Defaults to main.ahk if omitted.
  • Enabled: set to 0 to turn the plugin off without deleting the folder. Defaults to 1 if omitted.
  • Instances (optional): a comma-separated list of instance numbers to register hooks for only those instances (e.g. Instances=3,5). If omitted, applies to all instances.

main.ahk: declares exactly one class, named exactly the same as Class, that inherits from Plugin (extends Plugin). Example (verbatim from docs\Plugin\examples\HelloPacks\main.ahk):

class HelloPacks extends Plugin {
    static hookTarget := "PackOpening"

    afterEvent(ctx) {
        this.Log("Pack opening detected")
    }
}

That's it - there's no separate registration call to make. Declare which feature to attach to via static hookTarget, then override whichever of beforeEvent/afterEvent/onItem that target supports and that you need, from the catalog table below. The engine creates an instance at load time and calls it automatically.

The 3 General-Purpose Methods

Inheriting from Plugin lets you override the following 3 methods (the parent defaults are all no-ops):

  • beforeEvent(ctx) - called right before the action starts, if that hookTarget supports before.
  • afterEvent(ctx) - called right after it finishes, if it supports after.
  • onItem(ctx) - called once per item processed (a friend ID, an event name, a showcase ID, etc.), if it supports onItem (FriendAdd/FriendRemove/SpecialMission/Showcase).

Within one class, you can implement as many of that hookTarget's supported methods as you like at once (minimum 1 - implementing nothing fails validation; the maximum is however many methods that target supports). Implementing a method the target doesn't support isn't an error - it's simply never called (only a warning is logged during validation).

ctx.Get(key, default) - Safe Access to Conditional Fields

Many of the fields in the table above are conditional - for example, state in RunPhase.after only exists during the Prepare/Finish phases, and cards in GodPack.after is an empty string on the fallback path. Reading a conditional field directly as ctx.fieldName throws a PropertyError in AHK v2 the moment it isn't present.

Fire() automatically attaches a Get(key, default := "") method to every ctx right before calling the hook - the same convention as session.get()/botConfig.get():

value := ctx.Get("state", "")       ; "" instead of an exception if missing
count := ctx.Get("count", 0)

Fields that are guaranteed to always be present (e.g. id in FriendAdd.onItem, phase in RunPhase.before) are safe to read directly as ctx.fieldName - reserve ctx.Get() for conditional fields. Plugin.CTX_SHAPES in Plugin.ahk is the actual source of truth for "target.when → the complete set of field names that may be present" (this document is a prose copy of that). If code loads a field not present in CTX_SHAPES, PluginEngine.Fire() automatically logs a warning to Logs\Plugins.txt - a signal that "the docs/catalog have fallen behind the code."

Caution: because Fire() attaches Get to ctx via DefineProp every single time, serializing ctx itself wholesale with JSON.stringify(ctx) (including via Dump(ctx)) enumerates Get right along with everything else, which can subtly trip up an existing bug in Scripts/lib/JSON.ahk (property enumeration and the count used to decide comma placement use different criteria, leaving a trailing comma behind, among other things). When sending ctx somewhere external - a Discord webhook, for instance - don't pass ctx wholesale; pick out only the fields you need into a new object first.

4 Developer Convenience Functions

Separate from the gate functions (SessionRead, etc.), Plugin provides 4 instance methods for observation/debugging during development. Call these only from within beforeEvent/afterEvent/onItem - the loader doesn't populate this._name until after the instance constructor (__New()) finishes running, so if you override __New() and call these functions inside it, _name is still empty and things break (if you must override __New(), call super.__New() first - otherwise the _timers Map won't exist either, and TimerStart/TimerEnd will break too).

Target+Method Conflict Rule

If 2 or more plugins implement the same hookTarget + the same method (beforeEvent/afterEvent/onItem), only exactly 1 of them (the winner) is allowed to actually run for that method (the rest are ignored).

  • Determining the winner: alphabetical order of class name (ascending - the first one wins) - based on class name, not folder name. Folder names are usually the user's nickname and hard to adjust, but class names are freely chosen by the developer, so if you want to control your own priority, prefix the name with something like A_/Z_.
  • What happens to the loser: not the whole plugin - only the call to the conflicting method is skipped. Any other (non-conflicting) method the same plugin implements on the same target, or a separate plugin built against a different hookTarget entirely, is completely unaffected.
  • Relationship to the three-strikes rule - no bench player: if the winner later fails 3 times in a row and gets disabled for the rest of the session, that target.when simply stops being called - the runner-up does not take over. Conflict resolution is computed exactly once, at StartBot (load time), and never recalculated at runtime - if you need to swap out the winner, the user has to directly fix or disable the winning plugin.
  • Exception: PropertyError/MethodError disable immediately, on the first failure: the "3 consecutive failures" rule above applies to ordinary exceptions (a transient error like a network timeout). A PropertyError/MethodError (accessing a property/method that doesn't exist) is deterministic - retrying produces the exact same failure every time, so instead of the 3-strike grace period, a single failure disables that hook for the rest of the session. Practical implication: a plugin that reads a conditional field (e.g. picked in Wonderpick.after, which is only present on the CreateBots path and absent on the EventMission path) directly as ctx.fieldName will die for the entire session the very first time it's called without that field - using ctx.Get(key, default), described above, avoids this failure mode.
  • Results can differ per instance: if the Instances= ini key makes different plugins participate on different instances, the winner can differ from worker to worker. The Plugin Manager UI's static check only shows conflicts "assuming every plugin is registered on every instance," so the actual per-worker outcome may differ.
  • Plugin Manager UI display: the status column shows ⚠️ (structurally valid, but some methods are inactive because they lost to another plugin), and hovering over that row shows a color-highlighted tooltip indicating which method lost to whom (see the "Plugin Manager UI" section below).

Hook Execution Timeout

If a plugin hook hangs and never returns (an infinite loop, Sleep misuse, etc.), the entire worker hangs along with it - the engine has a watchdog to catch this. If a hook runs longer than HOOK_TIMEOUT_MS (5 minutes) without finishing, the worker is force-restarted by riding the existing stuck-recovery path (restartGameInstance, saving a screenshot via SaveStuckScreenshot, scheduling account cleanup, etc.) rather than some new restart path.

Limitation (be aware of this): because AHK v2 is single-threaded, this watchdog (a SetTimer callback) only fires at points where the currently running thread is "interruptible" (Sleep, the message pump, etc.). A pure tight loop with not a single Sleep in it (Loop { } with no wait at all) cannot be interrupted even by this watchdog - it's the best available defense, not a guaranteed forced termination. That said, all of this project's actual polling code (FindImageWithAction, etc.) is Sleep-based, so in practice this catches most "hang" situations.

The 4 ctx.phase Values - Only Present on RunPhase's before/after

What a plugin "attaches" to is chosen via static hookTarget (e.g. declaring hookTarget="RunPhase" attaches to RunPhase's before/after). phase is, specifically for the RunPhase target, simply a ctx.phase value that tells you which stage core is currently running through. It maps 1:1 to the 4 static methods on module\classes\PackOpeningRun.ahk.

Cross-Plugin Reference

To get another plugin's instance, use this.GetPlugin("OtherPluginName") (an instance method - internally a thin wrapper around PluginEngine.GetPlugin). The name is the folder name (the Name in plugin.ini), not the class name. It returns "" if that plugin is disabled or doesn't exist, so you must always guard it, e.g. if (other := this.GetPlugin("X")). Call this only from inside a hook (beforeEvent/afterEvent/onItem) - calling it at file top level may hit a point where that plugin hasn't loaded yet, depending on include order.

State Persistence - Two Layers

  • Values that only need to survive for the session: use an instance field on the class (this.someField) - since one instance is created per plugin, this.xxx works fine. Plugin code lives resident inside the worker process, so it already shares the same lifetime as the bot's session (session) - no separate registration/round-trip is needed.
  • Values that must survive a worker restart (reload/reconnect): use this.SaveValue("key", value) / this.LoadValue("key", defaultValue). These write to the [Plugin_<myFolderName>] section of the instance's own Scripts\N.ini - the section name itself is the ownership boundary, so it never mixes with another plugin's values.

Accessing Bot State (session/botConfig)

  • Reading: this.SessionRead(key), this.ConfigRead(key) - both can be read freely.
  • Writing: this.SessionWrite(key, value) - succeeds only for whitelisted keys (currently just keepAccount). A key not on the whitelist is silently rejected, and a warning is logged to Logs\Plugins.txt. botConfig has no write API at all (to persist settings, write plugin.ini directly).
  • If the value returned by SessionRead() is an object like an array/Map, treat it as read-only - mutating its internals corrupts core state directly.
This gate is a guardrail, not a security boundary. AHK v2 has no concept of private, so it can be bypassed by calling session.set() directly - its value lies purely in documenting the allowed scope in code and logging violations so diagnosis is faster.

Rules You Must Follow (violating these can hang or kill a worker)

  1. When calling FindImageWithAction inside a hook, you must always pass count: 1 or giveUpTime. Calling it with the defaults (count: -1, infinite polling) traps the worker inside that hook forever if the needle never appears.
  2. Never call ExitApp / Reload / Pause - the worker dies/freezes immediately.
  3. Never register SetTimer / Hotkey - interleaving with core's screen manipulation causes click races.
  4. Never access an owner object like session.run.xxx directly - use only the gate functions described above.
  5. Never do a blocking Sleep of several seconds or more - hooks run right in the middle of core's run loop.
  6. Prefix your own plugin's global functions/variables/needle names (e.g. MyPlugin_ or EBC_). A name collision with core or another plugin fails the load entirely (caught during the validation step below), excluding the whole plugin.
  7. Call the gate functions (SessionRead/SessionWrite/ConfigRead/SaveValue/LoadValue/GetPlugin) and the developer convenience functions (Log/TimerStart/TimerEnd/Dump/Screenshot) only from within beforeEvent/afterEvent/onItem - calling them inside __New() (the constructor) breaks because this._name isn't populated yet (see the "Developer Convenience Functions" section above).

Validation - Runs Automatically on Every StartBot

  1. Scan the folder, verify Name matches the folder name.
  2. Verify the Class= key is present in plugin.ini, and check via regex that main.ahk contains a class <Class value> extends Plugin declaration.
  3. Verify the static hookTarget := "..." value is one of the 17 entries in the hook target catalog above.
  4. Check via regex that at least one of beforeEvent(/afterEvent(/onItem( is implemented → fails validation if none are. If a method the target doesn't support is implemented, it still passes, but only a warning is logged to Logs\Plugins.txt (not fatal - it simply never gets called).
  5. Compute whether it conflicts with another (enabled, structurally valid) plugin that implements the same hookTarget+method (see the "Target+Method Conflict Rule" section above) - this result is exactly what the Plugin Manager UI's ⚠️ indicator and hover tooltip use.
  6. Copy any bundled .png files only if they're not already present in Scripts\Needles\ (shipped images are never overwritten).
  7. Combine all previously-passed plugins with this candidate and check 1.ahk as a whole without actually running it (parse-only) - if there's a problem, only this candidate is excluded, and the rest proceed as normal.
  8. If anything gets excluded, a single tray notification is shown, and the reason (down to what needs to be fixed) is logged to Logs\Plugins.txt.

Simply setting Enabled=0 in plugin.ini, or deleting the folder, excludes the plugin starting with the next StartBot.

Plugin Manager UI (PTCGPB.ahk)

There's a management screen so you don't have to edit plugin.ini by hand: Main window → the 🧩 tools icon → Tools & System Settings → 🧩 Plugin Manager button.

  • List: shows every folder under Plugins\ (including disabled ones). The leftmost checkbox toggles enabled state; the second column shows status - ✅ OK (passed structural validation + no conflicts + not a dead plugin) / ⚠️ (structurally valid, but some methods are inactive because another plugin won the conflict - shown in the reason column as "afterEvent: lost to <winning class name>" - since the conflict winner is determined by class name, it's displayed by class name) / ❌ (structural validation itself failed + reason). Whether it can actually be loaded into a worker (syntax errors, etc.) isn't checked here - that's only confirmed at StartBot time.
  • 🔴 Dead plugin: if every method it implements is one that its hookTarget doesn't support - so none of them ever get called - its name gets a 🔴 prefix, the status column shows ❌ No callable methods, and the checkbox is always drawn unchecked by default regardless of the Enabled value in plugin.ini (manually re-checking it isn't blocked - it's harmless anyway since no method ever fires).
  • ⚠️/🔴 row hover tooltip: hovering over the row shows a color-highlighted popup indicating which method lost to whom (a conflict), or which method isn't allowed on this target.
  • 🔄 Refresh: rescans the list. It's a pure read that doesn't touch any files, so it's fast.
  • 🗑 Delete: click a row to select it, then press this to delete that plugin's entire folder. Unlike disabling (unchecking the box), this can't be undone, so it goes through a confirmation dialog. This also deletes any needle images the plugin bundled from Scripts\Needles\, except when another remaining plugin uses the same filename, or it matches a core needle image name registered in NeedleRegistry.ahk (if either is uncertain, it errs on the side of not deleting - and Logs\Plugins.txt records why it wasn't deleted).
  • Apply/Save: writes the checkbox states immediately to each plugin.ini's Enabled. Takes effect starting with the next StartBot; has no effect on workers already running.
